## 3. ★成立を妨げている2点

### 3-1. 層厚が「片側だけ」— 両方揃うのは 20.7%

層厚の記載は豊富だが、**書き方が片側限定に偏っている。**

```
「層厚は500 m以上ある」        → min のみ（max 不明）  … 檜川層・脇野沢層・猿ヶ森層・泊層 ほか
「層厚は最大で1,800 mである」  → max のみ（min 不明）  … 四沢層・小坪川層・法量北溶岩 ほか
「層厚は200～800 mである」      → 両方 ✓               … 市ノ渡層・清水目層・浜田層・八幡岳溶岩
「層厚は約700 mである」        → 単一値（min=max とした）… 蒲野沢層・砂子又層
```

前回「野辺地はほぼ全ユニットに層厚がある」と報告したのは正しいが、
**「ある」と「Macrostrat の必須項目を満たす」は別だった。**訂正して補足する。

これは資料の書き方の問題であり、**同じ資料を読み直しても解決しない。**
取り得る選択肢は3つ。

| 案 | 内容 | 評価 |
| :--- | :--- | :--- |
| A | 片側のみで提出し、もう一方は空欄 | Macrostrat 側の扱いを要確認 |
| B | 片側のみのユニットに `status: CHECK` を立てて人間レビューへ回す | 現行50kパイプラインと同じ運用。**推奨** |
| C | 隣接図幅・5万分の1・原論文で補完 | 精度は上がるがコストが跳ねる |

### 3-2. lng / lat が資料に無い — 3 columns 中 0

**これが投入をブロックしている。**

Macrostrat の columns シートは `geom` または `lng`,`lat` のいずれかが**必須**。
しかし解説面には column の代表点となる座標が書かれていない。
地名（むつ市・七戸町・東通村…）と5万分の1地形図の区画名（むつ／七戸／野辺地／近川／陸奥横浜／平沼）はあるが、座標そのものは無い。

**ただしこれは解決できる。**同じ配信ページから **GeoTIFF + KML** が配布されている。

```
https://gbank.gsj.jp/ld/dlform/?url=/data/200KGM/GTF/GSJ_MAP_G200_NK5417_2021.zip
（GeoTiff, KML / 200dpi / 20 MB）
```

図幅の四隅座標が取れれば、地域区分ごとの代表点または `rgeom`（area of influence）を
作れる。**解説面テキストだけでは足りず、地質図面データとの併用が必須**という結論になる。

# 「200k補完による全国カバー計画」レビュー

**レビュー日**: 2026-08-11
**対象**: 20万分の一（200k）補完による全国地質データ100%カバー計画
**総合評価**: **方向性は正しいが、Macrostrat のデータモデルの理解に誤りがあり、このままでは提出しても通らない。**

---

## 0. 結論（先に）

| # | 指摘 | 深刻度 |
| :--- | :--- | :--- |
| 1 | **200kシームレスは `column` ではなく `map` に入れるデータ**。Macrostrat は両者を別系統で持っている | **致命的** |
| 2 | **「全国100%カバー」は column の目標ではない**。columns は面を埋めるものではない | **高** |
| 3 | **「2層レイヤー構造」は Macrostrat に存在しない概念**。columns は重ね合わせも優先採用もしない | **高** |
| 4 | **200k説明書PDFは1999年以降の刊行分にしかない**（実測で確認） | **高** |
| 5 | **`min_thickness`/`max_thickness` は Composite column の必須項目**。200kからは出ない | **高** |
| 6 | **累重順序を年代から自動生成するのは「解釈」**。プロジェクト規則「推測で値を埋めない」と衝突 | **高** |

**同時に、この計画には非常に価値の高い発見が埋まっている。**第4節に書き換え案を示す。

---

## 1. 【致命的】Macrostrat は column と map を別系統で持っている

計画は 200k を「広域Column」として出力するとしている。しかし Macrostrat の
データモデルでは、**面的な地質図ポリゴンは `map`（Burwell）系統**、
**層序累重は `column` 系統**であり、両者は別物である。

シームレス地質図V2 が持っているのは、
「この地点の岩体はこの年代・この岩相」という**面的属性**であって、
「A層の上にB層が乗り、その上にC層が乗る」という**累重関係ではない**。

年代順に並べて累重に見せることは可能だが、それは
**露頭で確認された上下関係ではなく、年代からの推定**である。
プロジェクト規則の「地層の対比が不確実な場合は、事実と解釈を明確に分ける」
「推測で値を埋めない」に正面から反する。

**map系統に入るべきデータを column系統に流し込むと、Macrostrat 側で拒否されるか、
通っても column DB の品質を落とす。**

---

## 2. 【重要】実測で分かったこと — この計画の本当の価値はここにある

Macrostrat API を一戸（北緯40.2 / 東経141.3）に対して直接叩いた。

### 2-1. 日本には Macrostrat の column が1本も無い

```
GET https://macrostrat.org/api/v2/columns?lat=40.2&lng=141.3&adjacents=true
→ {"data":[], "refs":{}}
```

**空。**つまり現在進めている 50k Column の作業は、**日本初の Macrostrat column** になる。
価値は計画書が想定しているより高い。

### 2-2. 日本の地質図として Macrostrat に入っているのは、世界図1枚だけ

```
GET https://macrostrat.org/api/v2/geologic_units/map?lat=40.2&lng=141.3
→ source_id 154
   "Chorlton, L.B. Generalized geology of the world"
   name: "Paleozoic-Mesozoic sedimentary rocks"
   lith: "sedimentary rocks"
   t_age: 66 / b_age: 358.9
```

一戸の地質が「古生代〜中生代の堆積岩、66〜359 Ma」としか記録されていない。
**GSJ のシームレス地質図は Macrostrat に入っていない。**

→ **シームレス地質図V2 を `map` source として Macrostrat に提供すれば、
日本の地質図解像度が 1:3,500万 から 1:20万 に一気に上がる。**
しかもベクタと凡例が既に整備されているので、**LLM が要らない。コストはほぼゼロ。**

**計画書が「LLMで200kからColumnを生成する」と書いている作業は、
やる必要が無い可能性が高い。**より簡単で、より正しく、より効果の大きい道がある。

| 項目 | 信頼度 |
| :--- | :--- |
| 日本に column が存在しない | **high**（API実測、2026-08-11） |
| 一戸の map source が Chorlton 世界図のみ | **high**（API実測） |
| シームレスが map source として未登録 | **medium**（1地点のみの確認。全国で網羅確認はしていない） |

## 3. 個別の技術的問題

### 3-1. 200k説明書PDFは半分程度しか存在しない ★計画の前提が崩れる

計画は「g200 説明書PDF を LLM に読ませる」を素材の中心に置いている。
しかし GSJ 地質図カタログに明記がある。

> 解説付（両面刷）は**1999年以降の発行から**。

実際に「北陸・中部及び近畿」15面を数えた。

| 解説面PDF **あり** | 解説面PDF **なし** |
| :--- | :--- |
| 輪島(2019) 富山(2023) 金沢(1999) 豊橋及び伊良湖岬(2004) 名古屋(2009) 伊勢(2010) 宮津(2022) 京都及大阪(2026) | 七尾･富山(1967) 高山(1989) 飯田(1990) 岐阜(1992) 木本(1992) 和歌山(1998) 田辺(1982) |
| **8面** | **7面** |

20万分の1地質図幅は1950〜90年代刊行が多く、**全国では「なし」の比率がもっと高い可能性がある。**
PDFが無い面はラスタ（JPEG/GeoTIFF）しか配信されていない。

→ **「200kで全国100%を埋める」は、説明書テキストを前提にする限り成立しない。**

### 3-2. `min_thickness`/`max_thickness` は Composite column の必須項目

Macrostrat の Format documentation（v0.1.1）より。

> ### Thickness
> - `min_thickness` / `max_thickness`
> These fields are **required for Composite columns only**.

200k の解説面には層厚が体系的には載っていない。シームレス地質図にも無い。
**必須項目が構造的に埋まらない。**

### 3-3. `b_pos`/`t_pos` の生成根拠が無い

同ドキュメントは、Composite column の位置について
「`b_pos`/`t_pos` が無い場合は行順から推定されるが、**推奨しない**（rows を並べ替えると
容易にデータが失われる）」としている。

200kから生成する場合、行順＝年代順にせざるを得ず、
**実質的に「推奨しない」経路に固定される。**

### 3-4. 「2層レイヤー構造」は Macrostrat に無い

計画の図は 50k を上層、200k を下層として重ねている。
Macrostrat の column にレイヤー優先度の概念は無い。
`rgeom`（area of influence）はあるが、これは「この column が代表する範囲」であって
上書き優先度ではない。

実際にやろうとしているのは重ね合わせではなく**タイリング（穴埋め）**だが、
そうすると次の幾何学的問題が出る。

- 50k図幅の範囲は矩形（緯度10分×経度15分）
- 穴埋め対象は「50k刊行済み矩形を全国から引いた残り」＝**非常に複雑な多角形**
- その多角形を200k図幅で切ると、**さらに細片化する**

この境界処理の設計が計画書に無い。

### 3-5. 「全国100%カバー」は column の目標ではない

Macrostrat の columns は、**地域を代表する層序累重**であり、
地図のように国土を隙間なく覆うことを目的としていない。
100%カバーは map 系統の目標である。

**map の目標を column に持ち込んでいる**のが、この計画の混乱の根にある。

## 4. 書き換え案

```text
【現行案】
  50k Column（上層）＋ 200k Column（下層で穴埋め）→ 全国100% column

【提案】
  ① 200k シームレス地質図V2 → Macrostrat の "map source" として提供
       LLM不要 / コストほぼ0 / 全国100%を即達成
       現在の 1:3,500万 世界図を 1:20万 に置き換える
  ② 50k 地質図幅 → 従来どおり "column" として提供

  ③ 200k を column 化するなら、解説面PDFがある1999年以降刊行分に限定し、
       低解像度 column として col_group / comments で明示ラベルする
```

**①と②は競合しない。むしろ Macrostrat 側では map と column が
互いにリンクされる設計なので、両方出せば相乗する。**

シームレス地質図（V1, V2）は **政府標準利用規約（第2.0版）準拠**。
出典を記載すれば、**改変を含む自由な二次利用が可能。利用申請手続き不要。**
Macrostrat は CC-BY 4.0 で配信しているので、出典表記の設計だけ詰めればよい。

## 5. フェーズ設定への指摘 ★最も実務的

### 5-1. フェーズ1（東北130面）の前に、フェーズ0が要る

本日時点の一戸1面の状態（`システム分析_20260811.md` より）。

```
一致 48 / 不一致 18 / 捏造 0 / 取りこぼし 137
Column: unsplit 1列（GOLD は west/central/east の3列）
```

**取りこぼし137、Column分割が未反映。1面がまだ通っていない。**

この状態で130面に広げると、**同じ失敗が130倍になるだけ**で、
何が悪いのかは1面のときより分かりにくくなる。

さらに未解決の基盤問題がある（`死んでいる部分_20260811.md` より）。

- **予算会計が二重化**（JSON側とSQLite側が互いの消費を知らない）
- `llm_limits.json` の `max_calls_per_day: 200` が実枠20と**10倍ずれている**
- 画像2ステージの生存候補が小型モデル2本のみ（`mistral-small` / `gemini-3.5-flash-lite`）

**予算ガードが機能していない状態で130面を回すのは危険。**
無料クレジットの消費が想定を超えても止まらない。

```text
【提案するフェーズ0】
  0-1. 予算会計をどちらか一方に寄せる（二重消費の停止）
```

```
     旧 地質調査所             → 産総研GSJが公開（全国）
     北海道開発庁              → 作業機関は道立地下資源調査所（北海道のみ）

② 北海道以外に、自治体が独自に5万分の1地質図幅を整備した例は見つからなかった。

③ ただし「全国のカバー率」は、まだ誰の数字も確定していない。
   GSJカタログの16地域ページを集計すれば出る。方法は確定したが未実施。
```

## 2. 体系の理解が間違っていた

GSJの5万分の1カタログは、**20万分の1の区画名で16グループ**に分かれている。


**GSJのカタログにも北海道（網走・釧路・旭川・札幌）は入っている。**

```
道総研の索引ページ（北海道）

  └─ gsj.jp へのリンク       :  51件
  掲載図幅（下限）           : 153面
```

**北海道については、道総研のページを見れば3機関分がまとめて手に入る。**
これが北海道だけ話が違って見えた理由。

5万分の1ではなく**県地質図（10万〜20万分の1）＋説明書**という形態と思われる。
これは50kの穴埋めには解像度が足りず、200kと同等以下。

→ **他府県の独自整備を当てにする必要は無い、という結論で進んでよい。**
　 ただし信頼度は medium。

## 4. 「全国カバー率」の数字を確定させる方法

### 分かったこと

GSJ公式（陸域地質図プロジェクト）に、1面あたりの範囲が明記されている。

> 地質図は，**約15 km × 20 km の範囲**を占め，3〜5年（のべ250日）かけて調査を行います．

```
1面 = 約300 km²
日本の陸域 = 約378,000 km²
→ 全面整備に必要な面数 ≒ 1,260面
```

### 訂正

前回のレポートで一戸図幅の面積を「約460 km²」と書いたが、**公式値は約300 km²。**
これに伴い、一戸(50k)と野辺地(200k)の解像度比の計算も修正が必要。

```
一戸(50k)   : 42 unit / 約300 km²    = 0.14 unit/km²
野辺地(200k): 29 unit / 約6,000 km²  = 0.005 unit/km²
→ 解像度比 約28倍（前回「約20倍」より大きい）
```

```

刊行済み面数を数える。
```

## [50k_columnization_plan_zfk_shapefile_20260813.md]

# GSJ 1:50,000資料の全国柱状図化計画 — ZFK・Shapefile統合版

作成日: 2026-08-13  
対象: GSJ 1:50,000地質図幅 763件  
最終目標: 人手作成GOLDと同等のColumn数・所属・順序・属性を、各図幅のGOLDを入力に使わず再現する

## 1. 結論

全国処理は、PDFの図版形式だけで経路を分けてはいけない。各図幅を次の二軸でルーティングする。

1. 構造化ソース階層: ZFK / Shapefile / PDF / Viewer画像
2. 柱状図表現型: 英語Vector / 日本語Vector / Raster / 異形Vector / 総括図なし / PDFなし

ZFKとShapefileは、地層ユニットの存在・名称・年代・岩相・地理分布を決定論的に与える。一方、Column数、Column所属、上下順序、同時異相、層序的不整合を単独で完全には与えない。したがって、構造化ソースを「正解の柱状図」ではなく、PDFの層序図・本文を復元するための台帳、空間制約、検算材料として使う。

## 2. 現在確認できている全国データ

`gsj_50k_inventory.json`（2026-08-08生成）と`gsj_50k_full_census.json`（2026-08-14 UTC生成）をmap_idで結合した結果は次の通りである。数字は本計画の着手時に再取得・再検証する。

### 2.1 構造化ソース階層

| Source tier | 図幅数 | 全国比 | 基本経路 |
|---|---:|---:|---|
| S1: ZFK + Shape + PDF | 121 | 15.9% | ZFK台帳 → Shape照合・空間制約 → PDFで層序復元 |
| S2: Shapeあり・ZFKなし | 282 | 37.0% | DBF台帳・ポリゴン → PDFまたはViewerで層序復元 |
| S3: PDFのみ | 254 | 33.3% | PDF図版・本文から台帳と層序を同時復元 |
| S4: Viewer画像のみ | 106 | 13.9% | 凡例・地質図画像のOCR/Vision → 人確認 |
| 合計 | 763 | 100% |  |

Shapeが利用できる図幅は合計403件で、全国の52.8%を占める。ZFK 121件は現行台帳上すべてShapeとPDFも利用できる。

### 2.2 PDF表現型と構造化ソースの交差

| PDF表現型 | ZFK+Shape | Shapeあり・ZFKなし | PDFのみ | Viewerのみ | 合計 |
|---|---:|---:|---:|---:|---:|
| Type 0: PDF未公開 | 0 | 2 | 0 | 106 | 108 |
| Type 1: 一戸型英語Vector | 0 | 1 | 4 | 0 | 5 |
| Type 2: 日本語Raster | 32 | 159 | 98 | 0 | 289 |
| Type 2: 日本語Vector | 19 | 6 | 27 | 0 | 52 |
| Type 3: 英語要約付きRaster | 24 | 53 | 22 | 0 | 99 |
| Type 4: 異形英語Vector | 4 | 1 | 21 | 0 | 26 |
| Type 5: 総括図なし | 42 | 60 | 82 | 0 | 184 |
| 合計 | 121 | 282 | 254 | 106 | 763 |

表中の「Shapeあり・ZFKなし」は、Type 0の2件を除きShape+PDFを意味する。

この交差表から、PDF表現型だけでパイロットを選ぶのではなく、同じ表現型についてS1/S2/S3を分けて評価する必要がある。

## 3. ソースごとの責務

### 3.1 ZFK

主用途:

- map_idに紐づく公式ユニットIDとユニット台帳
- 地層名、年代、岩相、説明などの構造化属性
- unit GeoJSONがある場合の分布形状
- Shapefile・PDFとの照合キーおよび競合検出

使わない推論:

- APIの配列順を最終層序順とみなさない
- ZFKに登録されていることだけでColumn所属を決めない
- ZFK欠落を「地層が存在しない」と解釈しない

### 3.2 Shapefile

主用途:

- `geo_A.dbf`の`MAJOR_CODE`、`SYMBOL`、`LEGEND01–04`和英属性によるユニット台帳
- `geo_A.shp`ポリゴンによるユニット分布、面積、重心、bbox、接触・近接関係
- ZFKとのmajor code・名称・年代・岩相の照合
- Columnの代表位置、Column footprint、共有ユニット、地下のみユニットの検証

使わない推論:

- DBFレコード順を確定層序順とみなさない
- 地図上の上下・南北関係を地層の新旧関係とみなさない
- 表層ポリゴンがないことを柱状図からの除外条件にしない
- ポリゴンの空間クラスタだけでColumn数を確定しない

### 3.3 PDF・Viewer画像

PDFの総括図、凡例、本文、地質断面図を、Column topologyの一次根拠にする。ここで復元するものは次である。

- Column数と名称
- 各ユニットのColumn所属（複数Column共有を含む）
- Column内の上下順序
- 不整合、整合、指交、貫入などの関係
- 層厚、堆積環境、本文だけにある年代制約

## 4. 新しい処理アーキテクチャ

### Stage A: Source manifest

全763図幅について、map_idを主キーに次を記録する。

- ZFK index・units・unit detail・GeoJSONの有無と完全性
- Shapefile ZIP、`geo_A.shp/.dbf/.shx/.prj`の有無と整合性
- PDF、Viewer、凡例画像、断面画像の有無
- PDF表現型、検出ページ、判定根拠、信頼度
- ファイルhash、取得URL、取得時刻、文字コード、CRS

「API上available」と「ローカルに完全取得済み」を分離する。ZFK 121件やShape 403件という件数は、実ファイルの取得・解析成功件数として再計算する。

### Stage B: Canonical unit registry

各図幅について、まずColumn未所属のcanonical unit registryを作る。

優先順位は固定の一列ではなく、フィールド別にする。

| フィールド | 第一候補 | 検算・補完 |
|---|---|---|
| unit ID / major code | ZFK | Shape |
| 地層名・年代・岩相 | ZFKとShapeの一致値 | PDF凡例・本文で競合解消 |
| Column所属・順序 | PDF総括図・本文 | Shape/ZFK空間分布で検算 |
| 層厚・境界・堆積環境 | PDF本文 | ZFK記述 |
| 地理形状・代表位置 | Shape polygon | ZFK GeoJSON、PDF地質図 |

ZFKとShapeの値が異なる場合は自動上書きせず、`source_conflict`として保存する。名称照合はmajor code、symbol、正規化和名・英名、年代・岩相の複合スコアを使い、曖昧な結合は保留する。

### Stage C: Column topology extraction

PDF表現型ごとに抽出器を切り替えるが、出力は共通のtopology graphにする。

- node: canonical unit
- column membership edge: unit → column
- order edge: older → younger
- relation edge: conformable / unconformable / interfingering / intrusive / unknown
- evidence: ページ、図番号、座標bbox、原文引用、抽出方式、confidence

経路:

1. Vector図: PDFの線・矩形・文字座標からColumn境界とセルを抽出
2. Raster図: 高解像度タイル化、OCR、Vision、線分検出を併用
3. 総括図なし: 本文の層序節、凡例順、上下関係文、断面図から仮想Columnを作る
4. PDFなし: Viewer凡例・地質図・断面画像を使い、証拠不足は明示してレビューへ送る

Column数は1–Nを動的に扱い、左右2列を前提にしない。

### Stage D: Spatial constraint and validation

ZFK GeoJSONまたはShape polygonがある図幅では、抽出したColumnに対して次を計算する。

- 所属ユニットのunion footprint、重心、代表点
- Column間の空間的分離度と重なり
- 共有ユニットの分布
- 本文の「西部・東部・北部・盆地・火山周辺」等との整合
- Columnに入ったがポリゴンのない地下・小規模ユニット
- 地図にあるがColumn/凡例から落ちたユニット

### Stage E: Attribute enrichment and normalization

### Stage F: Review and export

各値にsource、locator、原文、抽出方式、confidenceを付ける。人手確認は次へ集中させる。

## [北海道_調査結果_20260811.md]

# 北海道は空白ではなかった

**調査日**: 2026-08-11
**結論**: **私の前提が誤っていた。北海道は5万分の1地質図幅が6区画を除いて全域網羅されており、説明書PDFも公開されている。**

---

## 1. 結論

```
北海道立総合研究機構（旧 北海道立地下資源調査所）の公式ページに明記:

  「なお、北海道は6区画を除いて全域が網羅されています。」

未刊行はわずか6区画:
  女満別(網走-27) / 天塩(旭川-18) / 雄信内(旭川-19)
  今金(札幌-58) / 上ノ国(札幌-83) / 大千軒岳(札幌-89)
```

索引ページには **153図幅** が掲載され、そのうち **107本の説明書PDFが道総研サイトで直接公開**されている（残りは産総研GSJへのリンク）。

**200k も土地分類基本調査も日本地方地質誌も、北海道には要らない。**

---

## 2. なぜ見落としたか

**GSJ（産総研）のカタログだけを見ていたため。**

北海道の5万分の1地質図幅は、GSJ単独ではなく3機関が分担して整備していた。

| 発行機関 | 現在の管轄 |
| :--- | :--- |
| 旧 北海道立地下資源調査所（旧 北海道立地質研究所） | 道総研 エネルギー・環境・地質研究所 |
| 旧 地質調査所 | 産総研 地質調査総合センター |
| 北海道開発庁（当時） | 国土交通省 北海道開発局 |

道が整備した分は **GSJのカタログには載らない。**
「GSJの50k図幅が北海道で薄い」は事実だが、それは
**「北海道の50k図幅が薄い」を意味しなかった。**

前回まで3本のレポートで「北海道が三重に空白」と書いたが、
**その前提が最初から成立していなかった。**

## 3. 資料の性質（実物1本で確認）

「丸瀬布北部（網走-第23号）」1988年刊 の説明書PDFを実際に開いた。

### 層厚の記載例（すべて本文から）

### ★留意点 — OCR品質

テキスト層はあるが、**文字化けと数値欠落が散見される。**

```
「見掛けの層厚は、伊奈牛川で」   ← 数値が欠落
「万分の 地質図幅」              ← 「5万分の1」の数字が落ちている
「昭和63 11 月(1 988)」          ← 年月の桁が乱れている
「N.1.4」と「VI.1.4」が混在      ← ローマ数字の誤認識
```

1961〜1988年の紙資料をスキャンしてOCRしたものなので、**数値の信頼性が低い。**
層厚や年代を抽出する際は、**verbatim 引用と原文PDFの目視確認を必ず組み合わせる**必要がある。
現行の50kパイプラインが持つ「引用の文字単位検証」がそのまま効く場面。

## 1. ◎ 20万分の1地質図幅 解説面 — COSUNA 相当物が実在する


### 1-1. 層序総括図がある ★決定的

> **第1図「京都及大阪」地域の層序総括図**（鮮新統—完新統は省略 c：コンプレックス）

```
ろう石鉱床   「層厚 40~50m の層状を呈し」

高位段丘堆積物「層厚数 m~10m 程度」
```

```
「アルビアン期に堆積が始まり、沢田層の堆積はセノマニアン期まで継続した」
```

## 3. 変更内容（bootstrapのバッチ化が本体）

### 3.1 一から作れなかった理由（実測）

一戸の48ユニットinventoryは1応答で **約11,400 output token** を要する。
どのモデルも届かず、途中で切れたJSONが返っていた。

|---|---|---|

| gemini-3.6-flash | — | json_parse |
| bedrock mistral-large-3 | — | max_output 8,192 で送信前に遮断 |

### 3.2 直した内容: 2段バッチ化

`scripts/pdf_unit_bootstrap.py`

- **段A** `build_name_job()` — 名前の列挙だけ。予約出力 4,096
- **段B** `build_detail_job()` — 8件ずつ詳細。予約出力 `min(4096, 320×件数)`
- `run_batched_inventory()` — 段A 1回 + 段B Nバッチを実行し、決定的にマージ
- **検証は変えていない**。全バッチをマージしてから従来の
  `validate_inventory_response` を1回だけ通す。閾値も据え置き

実測（一戸）: **48 unit名 / 6バッチ / 外部call 7**、各応答は 95〜1,719 token で全て正常終了。

`executor` 注入時（GOLD/テスト）は**従来の単発パスのまま**。routerパスだけがバッチ化されている。

### 3.3 バッチ化に伴って直した副作用

| 事象 | 対処 |
|---|---|
| 不完全な在庫でも次providerへ切り替わらなくなった | 完全性判定を段Aの `validate_name_response` へ移動。閾値0.8は据え置き |
| ヒントが `Group` や正規表現の誤検出を要求し、到達可能な上限が0.778だった | `DIRECT_UNIT_HINT_PATTERN` から `Group` を除外。年代修飾の接頭辞を除去。ユニット接尾辞が2つ含まれる接着形を棄却 |
| `Zyūmonzi` と `Zyumonzi` が別物として数えられた | `_inventory_name_key` に NFKD + 結合文字除去を追加 |
| 部層5件をモデルが落としていた | 段Aのpromptに「memberはunitである。formationとは別に挙げよ」を明記 |
| バッチ結果を単発promptの版数で記録していた | 上位キャッシュの識別子を `BATCH_PROMPT_VERSION` から作るよう変更 |
